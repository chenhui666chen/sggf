# 小说创作链路融合式改进指导

> **文档状态（实施基线标注）**：本文是开工规格基线。P0–P4 五批已在主链路实施完成，
> 实施现状、测试记录与已知局限以 `docs/novel_pipeline_integrated_implementation_log.md` 为准。
> 本文与实施记录不一致处，以代码和实施记录为准；下文在关键分歧处标注了「已定方案」。

## 1. 目标与范围

本文用于指导小说模块吸收其他开源叙事引擎的有效思路，但不照搬其整体架构。

改造目标是增强本项目现有的：

- 五阶段开书流程
- 逐章“规划 -> 创作 -> 评审 -> 迭代”管线
- 多分区上下文装配和预算裁剪
- 人物卡、伏笔账本、质量记忆和一致性校验

改造后希望形成以下闭环：

```text
章节规划
  -> 细纲驱动的伏笔与连续性校验
  -> 受约束正文生成
  -> 质量评审与定向修订
  -> 写后结构化消化
  -> 状态、伏笔和质量记忆持久化
  -> 下一章按状态继续生成
```

本文不建议引入完整的新型叙事引擎、替换现有 Agent 编排，也不建议为了模仿单机项目而削弱本项目已有的数据库、任务队列、权限和人机协作能力。

## 2. 总体判断

当前小说模块的优势是生产流程和工程治理：

- 逐章生成已经拆成规划、创作、评审、迭代四步。
- 章节上下文按角色、关系、卷上下文、前文摘要、连续性资产、伏笔账本等分区装配。
- 质量评审已经有轻重失败码，并能驱动局部修订或实质重写。
- 有项目级质量记忆和伏笔登记机制。
- 有项目锁、配额、模型档位和后台任务治理。

当前小说模块的主要短板不是“没有功能”，而是多个机制尚未形成统一的叙事状态闭环：

1. 章节完成后已经会沉淀摘要、质量问题、伏笔账本和部分人物状态快照；真正缺少的不是把大纲字段再存一遍，而是缺少“正文相对细纲/规划的增量、偏差和证据”。
2. 框架级 `ForeshadowingTracker` 与章节级 `review_meta.foreshadow_ledger` 并行存在，生命周期没有统一。
3. `CONTINUITY_BREAK` 主要在正文生成后被发现；虽然章节规划已经接收大纲、卷上下文和伏笔信息，但缺少对“细纲伏笔任务是否能在当前状态下执行”的独立校验。
4. `build_character_runtime_brief()` 已经编译 `personality`、`worldview`、`limitation`、`growth_direction`，并在核心锚点、运行态摘要和 metadata 三个调用点传入。P0 不再补这四个参数，只做回归验收，并检查旁路是否同样完整。人物动态状态已有 `character_state_snapshots`，应复用而不是另建一套快照表。
5. 质量体系有失败码和记忆，但缺少章级张力趋势、文风漂移等长期指标。

## 3. 借鉴原则

### 3.1 借鉴机制，不复制产品形态

应吸收以下机制：

- 写后状态消化
- 细纲驱动的写前连续性闸门
- 伏笔到期和重要性调度
- 章节级张力趋势
- 文风漂移检测
- 结构化审计快照

不应直接复制：

- 单机 SQLite 替换现有 PostgreSQL
- 以守护进程替换现有 Celery/后台任务体系
- 以全新叙事图数据库替换现有模型
- 绕过人工确认，强制所有章节无人值守生成
- 另建一套与现有 `review_meta`、`ForeshadowingTracker` 平行的账本

### 3.2 增量落地

优先复用现有模块和数据流：

- 在现有 `routes_chapter.py` 增加写前检查和写后消化调用。
- 在现有 `chapter_post_save.py` 扩展状态提取，而不是新建独立章节管线。
- 在现有 `narrative_quality.py` 扩展质量指标和账本适配。
- 在现有 `character_runtime_context.py` 验收人物上下文编译。

## 4. 改进路线图

建议按以下顺序实施（实施状态见括号内标注）：

```text
P0 人物运行态与伏笔账本统一入口（✅ 已实施）
P1 细纲驱动的伏笔与连续性闸门（✅ 已实施）
P2 写后结构化消化（✅ 已实施基础版，含跨章债务滚动）
P3 量化质量监控（✅ 已实施基础版）
P4 人机协作与无人值守增强（✅ 主要路径已实施，重复输出检测待自动推进场景接入）
```

P0、P1 属于高收益的上下文和防错修复；P2 是长篇一致性的核心基础；P3、P4 建议在前三项稳定后实施。P0 的伏笔适配器只做读取和投影，P1 复用同一适配器做闸门，不要各自再定义一套字段。

## 5. P0：统一人物运行态与伏笔入口

### 5.1 人物运行态验收

当前代码已经具备本节原先设想的能力，不再作为开发项。

`build_character_runtime_brief()` 已接收并编译：

- `personality`
- `worldview`
- `limitation`
- `growth_direction`
- `speech_style`

三个调用点已完整传入：

- `build_character_runtime_metadata()`
- `build_core_character_anchor_context_from_text()`
- `build_character_prompt_context_from_text()`

本阶段只做验收和缺口检查：

- 两个性格不同的角色，运行态摘要可区分。
- 章节规划/正文 prompt 中能看到性格和价值倾向。
- 解析失败或字段为空时保持旧输出兼容。
- 预算紧张时动态状态优先于限制/成长方向。
- 检查是否还有未走上述三个函数的旁路，仍只注入身份和动机。

首章没有动态状态时，使用人物基线；续写时优先使用当前状态快照，再补充基线约束。

### 5.2 统一伏笔上下文适配器

当前存在两套伏笔机制：

1. `ForeshadowingTracker`：框架级生命周期 `planned/planted/paving/revealed/abandoned`。
2. `narrative_quality.py`：章节级 `open/recovered` 账本。

建议保留两层职责，但通过一个适配器统一输出：

```text
框架伏笔
  -> 章节级投影
  -> 当前章可执行任务
  -> 生成 prompt
  -> 章节后回收/推进
```

适配器输出统一采用 6.4 节结构。旧账本的 `open/recovered` 只作为兼容输入，映射到统一 `status` 后输出，不再单独维护第二套字段名。

不要在本阶段直接删除任何旧账本字段。先建立兼容读取和双向映射，再逐步迁移。

> **实施现状**：`backend/app/services/foreshadow_adapter.py` 已接入主链路，三层数据源为框架伏笔表格、章节 `review_meta.foreshadow_ledger` 与卷级文本（`epic_volumes_detail` + 卷上下文规则提取）。已知局限：卷级 `new_foreshadowings` 不持久化，只能从渲染文本规则抽取，属召回问题而非接线缺失；跨层归并保守（规范化文本相同且窗口不冲突才合并），同义异文的框架/卷条目仍可能保持两条，闸门对未合并条目会漏检，这是预期取舍。

### 5.3 P0 验收

- 核心人物 prompt 中能看到性格、价值倾向和限制。
- 两个身份相同但性格不同的角色，其运行态摘要可区分。
- 章节 prompt 使用统一格式读取未回收伏笔。
- 历史项目只有旧 `review_meta` 时仍能正常生成。
- 伏笔解析失败时回退为空或原始文本，不阻断章节生成。

## 6. P1：增加细纲驱动的写前连续性闸门

### 6.1 先明确职责：不是重复章节规划

当前章节规划已经根据大纲、当前卷上下文、人物、前文摘要、连续性资产和伏笔账本生成本章计划。因此，P1 不应再增加一个“重新规划章节”的 Agent。

```text
章节规划：提出本章要写什么
写前闸门：验证这个计划能否在当前叙事状态下执行
正文生成：把通过验证的计划写成正文
写后评审：检查正文是否真正执行计划且没有产生新矛盾
```

写前闸门只做规则优先的结构化校验，不评价文学性，不重新判断大纲优劣，也不替代正文质量评审。

### 6.2 大纲拓展已经提供的伏笔字段

大纲拓展已经在不同层级提供伏笔信息：

#### 史诗框架层

关键伏笔布局包含：

```text
伏笔内容 / 埋设位置 / 铺垫卷 / 揭秘卷
```

可映射到框架伏笔主档案：

| 大纲字段 | 主档案字段 |
|---|---|
| 伏笔 | `content` |
| 埋设位置 | `planted_volume` / `planted_chapter` |
| 铺垫卷 | `pave_volumes` |
| 揭秘卷 | `reveal_volume` |

#### 卷细纲层

`volume_connector.py` 会提取：

- `new_foreshadowings`
- `ending_hook`
- `next_volume_target`
- `character_status_update`

这些信息承担跨卷承接，但 `new_foreshadowings` 目前主要是摘要字符串，不是稳定伏笔实体。

#### 章细纲层

章细纲包含：

```text
场景目标 / 冲突设计 / 关键事件 / 涉及人物 / 人物推进
情节作用 / 结尾钩子 / 爽点类型 / 伏笔事项
```

其中 `情节作用` 可以表达“承接、升级、转折、爆点前置、伏笔回收”，`伏笔事项`表达本章新埋设或回收的伏笔。

因此，写前闸门的对象不是“章节规划有没有参考大纲”，而是：

```text
章细纲伏笔任务
  -> 章节规划是否正确执行
  -> 是否符合框架的埋设/铺垫/揭秘窗口
  -> 是否具备当前状态所需的前置条件
```

### 6.3 三层伏笔链路与当前缺口

当前项目存在三层伏笔来源：

```text
史诗框架伏笔布局 -> ForeshadowingTracker
卷细纲伏笔摘要   -> volume_connector.py.new_foreshadowings
章细纲/章节规划  -> review_meta.foreshadow_ledger
```

目标链路应当是：

```text
框架伏笔主档案
  -> 卷级任务投影
  -> 章细纲伏笔任务
  -> 章节规划执行计划
  -> 正文执行证据
  -> 伏笔状态推进
```

当前缺口：

- 三层数据没有统一伏笔 ID。
- 框架中的“主角真实身份”和细纲中的“身世线索”主要靠文本相似度关联。
- 埋设卷、铺垫卷、揭秘卷没有稳定下沉到章级任务。
- `情节作用` 与 `伏笔事项` 没有机器校验。
- `recovered` 通常只记录章节号，没有正文证据片段和回收类型。

P1 不应新建第三套伏笔系统，而应先建立兼容适配器，统一输出三层伏笔任务。

### 6.4 统一伏笔任务结构

适配器至少应输出：

```json
{
  "id": "fs_identity_001",
  "content": "主角真实身份",
  "status": "planned|open|paving|revealed|recovered|abandoned",
  "action": "plant|pave|continue|reveal|none",
  "importance": "critical|important|normal|minor",
  "planted_volume": 1,
  "pave_volumes": [2, 3, 4],
  "reveal_volume": 5,
  "source": "framework|volume_outline|chapter_outline|chapter_plan",
  "chapter_requirement": "本章只允许通过异常细节进行暗示",
  "evidence": ""
}
```

兼容旧数据：没有 `id` 时生成稳定的规范化临时键；只有文本摘要时保留 `source` 和低置信度标记；旧 `open/recovered` 状态不强行推断完整生命周期。

跨层归并规则首期必须保守，宁可两条暂不合并，也不要误并成一条：

```text
同一条伏笔（可自动合并）
  规范化后的核心名词完全相同，例如“主角真实身份”
  或框架 ID 已被卷/章细纲显式引用

疑似同一条（只关联，不合并）
  文本相似度高，但一方缺埋设/揭秘窗口
  一方是隐喻，一方是直述

不是同一条（禁止合并）
  揭示对象不同
  揭秘卷/章窗口明显不同
  一条是核心身份，一条只是局部道具异常
```

临时键只用于单层去重，不能作为跨层永久 ID。只有框架层明确条目，或人工/高置信确认后的条目，才能升级为稳定 `fs_*` ID。

### 6.5 闸门检查内容

首期只检查高置信度规则，避免复杂 LLM 判断阻断正常创作。

#### A. 伏笔动作与细纲一致性

- 细纲标记 `reveal`，章节规划是否明确回收对应伏笔。
- 细纲标记 `pave`，章节规划是否错误写成完整揭示。
- 细纲标记 `none`，章节规划是否无理由新增核心跨卷伏笔。
- `情节作用=伏笔回收` 时，`伏笔事项` 是否有对应目标。
- `伏笔事项=无` 时，是否错误声明本章回收伏笔。

#### B. 框架窗口一致性

- 当前卷是否允许埋设该伏笔。
- 当前卷是否属于允许铺垫范围。
- 当前卷是否早于规定的揭秘卷。
- 当前章节是否早于明确的揭秘章节。

#### C. 回收前置条件

- 伏笔是否已经标记为 `recovered/revealed`。P1 即可做。
- 关联角色是否已经登场。P1 只使用现成数据：`appearance_status`、`life_status`、角色识别结果；不要等待 P2 事件图。
- 关键道具、地点或设定是否已经建立。P1 只检查设定清单和角色 JSON 中已有字段；完整“本章是否建立”要等 P2。
- 伏笔要求的前置线索是否已经出现。P1 若没有稳定证据，只给 warning，不 blocking。

也就是说，C 类检查要拆成两期：

| 检查项 | P1 | P2 之后 |
|---|---|---|
| 已回收/已揭示状态 | blocking | 增加正文证据 |
| 角色生死/出场状态 | 可用现成字段 blocking | 用事件证据复核 |
| 道具/设定已建立 | 仅设定清单 warning | 可用事件/债务 blocking |
| 前置线索已出现 | warning 或跳过 | 可用未闭合事件 blocking |

#### D. 章节承接

- 上一章结尾钩子是否在本章计划中有承接。
- 上一卷 `new_foreshadowings` 是否在本卷开局目标或章节任务中得到安排。
- 本章是否跳过尚未处理的伏笔或关键冲突。

#### E. 计划内部一致性

- `情节作用`、`伏笔事项`、`关键事件` 三者是否互相矛盾。
- 章节定位是否与伏笔动作冲突。
- 章节计划是否同时写“只暗示”和“明确揭示”。
- 本章涉及人物是否包含伏笔任务所需的关键角色。

#### F. 通用连续性

- 角色是否已死亡、离场或尚未登场。
- 当前计划是否违反角色能力限制或当前阵营。
- 当前计划是否重复完成已完成且无新变化的关键事件。
- 当前计划是否引入与当前卷目标无关的新主线。

### 6.6 结果分级与失败处理

```text
blocking：必须重规划
warning：允许生成，但进入正文 prompt 和评审重点
info：仅记录
```

建议复用现有失败码：

| 检查问题 | 复用码 | 建议级别 |
|---|---|---|
| 提前揭示或错误回收伏笔 | `CONTINUITY_BREAK` | blocking |
| 计划与伏笔前置条件冲突 | `LOGIC_BREAK` | blocking |
| 角色行为违背人物基线 | `OOC_MAJOR` | blocking/warning |
| 细纲要求推进但计划没有实质推进 | `STALL_NO_PROGRESS` | warning |
| 伏笔长期未铺垫 | `CONTINUITY_BREAK` | warning |

结果应带阶段字段：

```json
{
  "code": "CONTINUITY_BREAK",
  "phase": "pre_generation",
  "severity": "blocking",
  "foreshadowing_id": "fs_identity_001",
  "evidence": "第 3 卷细纲要求铺垫，章节计划却明确揭示身份真相"
}
```

blocking 不应丢弃用户已有章节：保存规划草稿和报告，只让规划 Agent 修改冲突部分，自动重规划默认不超过 2 轮，仍失败则进入人工确认。

### 6.7 与正文生成和写后评审的边界

```text
写前闸门：这个计划是否可以执行
正文生成：按计划写作
写后评审：正文是否按计划执行且没有新矛盾
写后消化：把正文变化写回状态、伏笔和事件记录
```

即使章节规划已经基于大纲生成，正文仍可能提前揭示、漏写或改写伏笔，因此写后评审仍然保留。写前和写后结果分别使用 `phase=pre_generation` 与 `phase=post_generation`。

## 7. P2：增加写后结构化消化

### 7.1 目标

章节保存后追加一次结构化提取，但不是把大纲、细纲已经确定的内容再完整入库一遍。

大纲、细纲和章节规划已经确定的是“计划”：

```text
本章要发生什么
本章要出场谁
本章要埋设/铺垫/回收哪条伏笔
本章人物应如何推进
```

写后消化要确认的是“执行结果”：

```text
正文实际发生了什么
计划是否被提前、推迟、改写或遗漏
人物状态是否真的变化
伏笔是否真的推进或回收
新增了哪些计划外事实
```

因此，P2 采用增量沉淀，不采用全量重写：

| 内容 | 是否需要章后沉淀 | 原因 |
|---|---|---|
| 框架伏笔主档案 | 否，只引用 | 大纲阶段已经确定 |
| 章细纲中的场景目标、冲突、关键事件 | 否，只对照 | 这是计划，不是结果 |
| 伏笔是否按任务执行 | 是，只记状态变化和证据 | 正文可能提前揭示、漏写或改写 |
| 人物当前动机、情绪、关系变化 | 是，只记变化项 | 细纲只写“应推进”，不写本章结束时的实际状态 |
| 计划外新增事实、新角色、新伏笔 | 是 | 正文经常产生计划外信息 |
| 因果关系 | 只记关键因果 | 不需要把每句动作都做成图谱 |
| 未变化的人物/伏笔/设定 | 否 | 没有增量就不要重复落库 |
| 完整正文复述 | 否 | 摘要已经覆盖阅读用途 |

建议最小产物只保留增量：

- 相对细纲发生偏差的关键事件
- 计划外新增事实
- 真正发生变化的人物状态
- 伏笔推进/回收证据
- 未兑现的叙事债务

当前 `chapter_post_save.py` 已经会生成摘要、做人物行为检查，并尝试提取人物状态快照。P2 应复用这些写入端，而不是再开一套平行消化管线。

> **已定方案**：轻量与重量字段全部走 `chapter_post_save` 异步抽取（`narrative_state_extractor.py` 一次 LLM 输出），不扩展评审 prompt。
> 人物状态变化、伏笔短证据、事件偏差、关键因果、叙事债务和张力 5 指标同一次消化产出；评审步只保留失败码与修订判断。
> 理由：评审输出接近 token 上限时回退代价高；消化失败不影响正文保存，本章增量可下章补抽。

### 7.2 推荐输出结构

```json
{
  "chapter": 12,
  "events": [
    {
      "id": "evt-12-01",
      "description": "林烬拒绝交出证物",
      "participants": ["林烬", "沈砚"],
      "causes": ["evt-11-03"],
      "consequences": ["沈砚开始怀疑林烬"],
      "evidence": "原文片段"
    }
  ],
  "character_changes": [
    {
      "character": "林烬",
      "field": "current_motivation",
      "before": "查明旧案",
      "after": "保护证人并查明旧案",
      "reason": "目睹证人遇袭",
      "evidence": "原文片段"
    }
  ],
  "foreshadowing": [],
  "narrative_debts": [],
  "confidence": 0.86
}
```

如果本章完全按细纲执行、没有人物状态变化、也没有计划外事实，写后消化可以只输出：

```json
{
  "chapter": 12,
  "plan_alignment": "matched",
  "events": [],
  "character_changes": [],
  "foreshadowing": [
    {
      "id": "fs_identity_001",
      "action": "pave",
      "status": "open",
      "evidence": "正文中出现异常细节，但未揭示"
    }
  ],
  "narrative_debts": []
}
```

也就是说，计划本身不需要再沉淀一次；需要沉淀的是“执行证据”和“相对计划的增量”。

`character_changes` 的增量判定不另写一套变化检测：现有 `character_state_extractor.py` 已经输出 `current_motivation` / `current_belief` / `emotional_state` / `relationship_state` / `known_information` / `state_changes` / `evidence`，并幂等落库到 `character_state_snapshots`。P2 应将本章提取结果与上一章最新快照逐字段对比，只沉淀真正变化的字段；未变化项不落库。

### 7.2.1 这些产物如何被下一章使用

沉淀不是为了再存一份细纲，而是把“本章结束后的世界状态”交给后续四个环节：

```text
下一章规划
写前闸门
正文生成
写后对照 / 质量评审
```

当前项目已经有部分注入位：`structured_memory`、`recent_chapter_assets_summary`、人物状态快照。P2 的产物应优先接入这些现有入口，而不是另开一套 prompt 分区。

#### 事件

用途：告诉后续章节“哪些事实已经发生，不能再当未发生”。

- 下一章规划：优先承接最近未完成事件，避免跳过刚发生的冲突。
- 写前闸门：如果计划让角色重复完成已发生事件，或否认已发生事实，判 `STALL_NO_PROGRESS` / `LOGIC_BREAK`。
- 正文生成：作为“已知事实”，防止角色不知道自己刚做过的事，或把已完成动作再写一遍。
- 写后对照：比较本章正文是否兑现了上一章留下的事件后果。

只注入最近 1-3 个未闭合、会影响下一章选择的事件，不把整章事件列表塞进 prompt。

#### 因果

用途：约束“为什么现在必须这样写”，不是做文学分析。

- 下一章规划：根据 `A 导致 B` 选择本章必须处理的后果，而不是另开无关冲突。
- 写前闸门：如果计划让结果发生，但原因事件尚未发生，判 `LOGIC_BREAK`。
- 正文生成：限制角色动机必须能追溯到上一章原因，例如“因为拒绝交证物，所以沈砚开始怀疑”。
- 写后对照：检查正文有没有把结果写成无因突变。

只保留会影响后续选择的关键因果，例如身份暴露、关系破裂、承诺未兑现、能力受限。日常动作因果不入库。

#### 人物变化

用途：把细纲里的“应推进”变成下一章可用的“当前状态”。

- 下一章规划：按人物当前动机、情绪、关系和已知信息安排出场与冲突，而不是按初始角色卡安排。
- 写前闸门：如果计划让角色使用已经改变的立场之前的旧态度，或让已破裂关系立刻恢复，给出 warning / blocking。
- 正文生成：注入 `current_motivation`、`emotional_state`、`relationship_state`、`known_information`，覆盖静态 `profile` 中过时的当前处境。
- 写后对照：检查本章人物变化是否有事件证据，没有证据则不更新快照。

当前 `character_state_snapshots` 已经存在，是人物变化的正确落点。P2 只应在“本章确实变化”时更新快照，并在下一章 `build_chapter_generation_context` 中优先使用最新快照。不要再规划一张同名新表。

#### 叙事债务

用途：记录“答应了但还没还”的内容，防止长篇后半段遗忘。

叙事债务不是新的伏笔主档案，而是执行层欠账，例如：

```text
上一章结尾钩子尚未兑现
细纲要求回收但正文只暗示
角色当众承诺尚未履行
新出现的问题还没有处理
计划外新增线索还没有归属
```

- 下一章规划：把到期或高优先级债务放进本章必须处理项，而不是继续开新线。
- 写前闸门：如果本章定位允许处理该债务，但计划完全无视，给出 warning；连续多章无视同一高优先级债务，升级为 blocking。
- 正文生成：作为“必须承接的未完成事项”注入，优先级高于新开冲突。
- 写后对照：如果正文处理了债务，标记部分偿还或已偿还，并留下证据；如果再次遗漏，增加逾期计数。

债务应和伏笔分开：伏笔是大纲规划对象，债务是正文执行后仍未闭合的缺口。一条伏笔可以派生出债务，但债务不应自动升格成新的核心伏笔。

#### 注入优先级

下一章上下文应按下面顺序使用，避免把所有产物平铺进 prompt：

```text
1. 本章细纲任务
2. 未偿还且到期的叙事债务
3. 最近人物状态变化
4. 最近未闭合事件及其关键因果
5. 框架/卷级伏笔任务
6. 摘要和 RAG 细节
```

这样下一章看到的不是“上一章全文结构化复述”，而是：

```text
必须先处理什么
哪些事实已经成立
人物现在处于什么状态
哪些计划还没还上
```

### 7.3 持久化建议

第一阶段可以继续存入 `review_meta` 下的版本化 JSON，降低迁移风险。**落库约束**：任何写入 `project_settings.review_meta` 的路径必须先读取旧值再顶层合并；禁止用当章评审对象整包覆盖，否则 `narrative_state_v1` / 债务滚动会被冲掉。



```text
review_meta.narrative_state_v1
```

当结构稳定、查询需求明确后，再迁移尚未独立的部分：

- 复用已有 `character_state_snapshots`
- 新增 `chapter_events`（仅未闭合或偏离计划的事件）
- 新增 `chapter_causal_edges`（仅关键因果）
- 新增 `narrative_debts`

人物静态基线和当前章节状态必须分开存储。不能用本章状态覆盖 `Character.profile` 或原始角色基线。

### 7.5 上下文容量与思考模式约束

这些产物接入后，不能采用“所有字段完整拼接”的方式。当前章节规划已经有模型级安全预算：通常按模型上下文窗口的约 60% 计算输入预算，并预留输出 token 和 prompt 固定开销；历史章节上下文还单独受限于安全输入预算的一小部分。这个保护必须保留。

目标应是：

```text
完整保留高价值状态
  + 尽量少截断关键字段
  + 低价值历史信息分层压缩
  + 给输出和服务端开销留出固定余量
```

#### 分层预算

建议为下一章规划和正文分别建立预算，不共用一个无限增长的字符串：

| 层级 | 内容 | 策略 |
|---|---|---|
| T0 强制 | 当前章细纲、blocking/warning、到期叙事债务、当前人物状态、上一章未闭合事件 | 尽量完整，不做头尾截断；超预算时只压缩证据文本 |
| T1 重要 | 本章相关伏笔任务、关键因果、最近 2-3 章连续性资产、核心角色锚点 | 保留结构字段和动作，压缩解释段落 |
| T2 可压缩 | 近 5-10 章摘要、项目质量记忆、卷上下文 | 分层摘要，保留最近和高优先级项 |
| T3 可牺牲 | 远期历史、低相关 RAG、已闭合事件、无变化人物 | 优先删除，不影响生成 |

事件、因果、人物变化和债务应作为结构化短记录注入，而不是把原文证据全文带入。每条记录建议包含：

```text
id / 状态 / 当前动作 / 一句话摘要 / 影响对象 / 证据短摘录
```

证据只用于解释和校验，正文 prompt 默认只注入短摘录；需要追溯时再通过 ID 查询完整正文。

#### 规划和正文使用不同上下文

章节规划需要看到更多“计划和约束”：

- 当前章细纲完整字段
- 伏笔动作、窗口和前置条件
- 未偿还债务
- 近期人物与事件状态

正文生成只需要看到“已确认执行状态”：

- 规划结果
- T0 当前状态
- 本章必须承接的事件/债务
- 相关角色和伏笔的短摘要

不要把规划阶段的全部大纲、完整历史摘要和全部 RAG 再复制到正文 prompt。

#### 思考模式策略

小说正文和章节规划默认不启用额外思考模式或扩展 reasoning budget。原因是思考 token 与输入上下文、输出正文共用模型上下文上限，开启后会直接压缩可用正文空间。

建议规则：

1. 章节规划、正文生成、章节重写默认使用非思考模式。
2. 写前闸门优先使用本地规则校验，并复用协同扩展中已有的角色识别与人物-情节对齐能力，不调用带长思考的 LLM。`CharacterPlotValidator` 更偏大纲阶段匹配度分析，不能原样当作逐章在场/生死闸门；可复用其角色清单、出场判断和规则层，不要把整段大纲评审 prompt 搬进逐章生成。
3. 必须使用模型判断时，使用短 JSON 输出、低 token 上限、独立小上下文，不把思考过程回填到正文 prompt。
4. 质量评审可以单独使用更强模型，但评审输入和正文生成输入分开计算预算。
5. 不把 `reasoning_content`、隐藏思考文本或长分析结果写入 `structured_memory`、`recent_chapter_assets_summary` 或人物状态快照。

如果供应商模型默认开启 reasoning，应在模型路由层显式关闭，或将 reasoning budget 设置为 0/最小值，并在请求日志中记录最终生效配置。不能只依赖 prompt 中的“不要思考”，因为这不会释放服务端实际预留的推理 token。

> **实施现状**：规划、重规划、正文与写后消化已关闭思考模式。评审、迭代计划、改稿与复评也已关闭思考模式。空输出、占位模板以及与上一章高度重复的正文会触发 `empty_output` 熔断。

#### 预算计算与降级顺序

建议沿用现有 `_get_safe_input_token_budget()` 和 `_estimate_tokens_by_chars()`，在此基础上给新增状态预留独立预算，不改变现有模型窗口估算：

```text
总上下文预算
  - 固定系统 prompt
  - 预留输出 token
  - 服务端/工具开销
  = 可用输入预算
```

输入超限时按以下顺序降级：

1. 删除已闭合事件、已偿还债务和低相关 RAG。
2. 合并重复事件和重复伏笔，只保留 ID、状态和最新证据。
3. 压缩 T2/T3 摘要，不截断 T0 结构字段。
4. 压缩 T1 的证据和解释，只保留短摘录。
5. 最后才减少历史章节数量。
6. 如果仍超限，返回可解释的预算错误或切换到更大上下文模型，不静默丢掉当前章细纲和 blocking 结果。

建议在日志和测试中记录每个分区的：原始 token、注入 token、截断状态和降级原因。这样才能验证“少截断”是真实发生，而不是只看到最终 prompt 变短。

### 7.6 失败降级

写后消化失败不得使已成功生成的章节回滚为不可用。应：

- 保存正文。
- 记录消化任务失败。
- 使用现有章节摘要和伏笔账本作为回退。
- 在下一章上下文中标记“状态提取不完整”。

## 8. P3：增加量化质量监控

### 8.1 章节张力趋势

建议新增章级指标，而不是追求复杂的逐句评分：

- `tension_score`：0-100
- `conflict_progress_score`：0-100
- `emotion_change_score`：0-100
- `information_gain_score`：0-100
- `ending_hook_score`：0-100

保存到章节质量元数据中，并计算最近 5-10 章趋势。

触发策略：

- 连续两章低于阈值：进入规划诊断。
- 单章异常低但章节定位允许低谷：只记录，不强制重写。
- 结尾钩子和推进分同时过低：进入定向修订。

### 8.2 文风漂移

首期不必引入复杂向量服务，可采用：

1. 选定项目级文风样本。
2. 对章节生成文本计算轻量风格特征。
3. 对超阈值章节触发风格修订提示。

风格特征可以包括：

- 平均句长
- 对话占比
- 叙述/动作/心理描写比例
- 高频连接词和套话
- 视角切换频率

风格漂移只能作为修订信号，不能直接覆盖用户稿件。
首期不要把“叙述/动作/心理比例”做成必须 LLM 判断的指标。中文网文句长和对话占比区分度有限，P3 只做可计算的浅层特征；需要语义判断的风格项后置。

### 8.3 与现有失败码融合

量化指标不应替代失败码，而应作为证据：

```text
tension_score 低 + STALL_NO_PROGRESS
voice_drift 高 + AI_TRACE / DIALOG_STIFF
emotion_change 低 + EMOTION_FLAT
```

这样仍然保留现有的局部修订/重写路由。

## 9. P4：增强人机协作和无人值守能力

本项目定位不是纯无人值守系统，因此建议采用“可暂停的自动推进”，而不是强制全自动。

### 9.1 自动推进条件

只有满足以下条件才允许自动进入下一章：

- 写前闸门无 blocking 问题。
- 质量评审无高严重度失败码。
- 伏笔和人物状态消化成功，或有明确降级标记。
- 当前章节质量指标不低于项目阈值。
- 自动修订轮数未超过上限。

### 9.2 熔断条件

出现以下情况应暂停项目，而不是继续生成：

- 连续章节出现 `CONTINUITY_BREAK`。
- 同一质量问题连续高频复发。
- 结构化状态提取连续失败。
- 伏笔账本出现无法解析或状态冲突。
- 模型输出为空、重复或明显偏离章节规划。

暂停后保留：

- 章节草稿
- 闸门报告
- 评审报告
- 消化结果
- 当前状态快照
- 重试计数

## 10. 数据与接口兼容要求

### 10.1 不破坏现有数据

- 保留 `profile` 作为完整人物档案回退。
- 保留 `review_meta.quality_memory` 和旧伏笔字段读取能力。
- 新增字段全部可空或提供默认值。
- 历史项目不需要一次性重跑全部章节。

### 10.2 版本化结构化产物

所有写后消化结果必须带版本号：

```text
narrative_state_v1
```

版本升级时保留旧版本，避免历史章节无法读取。

### 10.3 幂等性

以 `project_id + chapter_id + extractor_version` 作为消化结果的幂等键。重复执行章后任务不能重复追加事件、关系和伏笔。

## 11. 测试计划

### 11.1 P0 测试

- 人物性格/价值观进入运行态摘要。
- 伏笔两套数据可以转换成统一输出。
- 旧格式 `review_meta` 可继续读取。

### 11.2 P1 测试

- 正常规划通过闸门。
- 角色死亡后再次出场被识别为 blocking 或 warning。
- 重复推进被识别为 `STALL_NO_PROGRESS`。
- 章细纲要求 `pave`、章节规划却执行 `reveal` 时被识别为 blocking。
- 当前卷早于框架揭秘卷时，提前回收核心伏笔被识别为 `CONTINUITY_BREAK`。
- `情节作用=伏笔回收` 但 `伏笔事项=无` 时产生结构化问题。
- 旧伏笔账本没有统一 ID 时仍能兼容读取，且不会重复登记。
- 闸门重规划达到上限后返回人工确认。

### 11.3 P2 测试

- 无增量章节只保存对照结果和必要证据，不重复写入细纲原文。
- 有增量章节保存事件偏差、人物变化、伏笔证据和叙事债务。
- 消化失败不影响正文保存。
- 重复任务幂等。
- 人物基线不被动态状态覆盖。
- T0 字段在预算压力下不被静默删除。
- 章节规划和正文生成默认不携带额外思考预算。

### 11.4 P3/P4 测试

- 质量趋势正确计算。
- 低谷章节不会被错误强制重写。
- 连续失败触发熔断。
- 人工确认后可恢复自动推进。

## 12. 验收标准

改造完成不以“新增了多少表或多少 Agent”为标准，而以以下行为验收：

1. 写作 prompt 能稳定获得核心人物的性格、价值观、限制和当前状态。
2. 伏笔不会因为框架账本和章节账本分裂而重复登记或丢失。
3. 正文生成前能阻断高置信度的角色、设定和推进冲突。
4. 章节完成后能提取相对细纲的增量：事件偏差、关键因果、人物变化和叙事债务，而不是全量复述细纲。
5. 下一章优先使用结构化状态，同时保留原始文本回退。
6. 质量指标能够表现趋势，而不是只对单章输出一次性评分。
7. 自动推进可暂停、可恢复、可审计，不会覆盖用户稿件。
8. 历史项目和旧数据无需破坏性迁移即可继续创作。

落地验收应补量化指标，首期建议：

| 批次 | 工作量量级 | 量化验收 |
|---|---|---|
| 第 1 批：运行态验收 + 伏笔读取适配 | 小 | 核心角色 prompt 含性格/价值观；旧账本可读；误合并为 0 |
| 第 2 批：P1 闸门，不含完整 C 类事实图 | 中 | 高置信冲突阻断；细纲文本解析失败只 warning；误报率先人工抽检，目标低于明显误伤 |
| 第 3 批：增量消化 | 中到大 | 无增量章节不重复写细纲；消化失败不影响正文；幂等 |
| 第 4 批：张力/浅层文风 | 中 | 低谷章不误强制重写；风格分不覆盖用户稿 |
| 第 5 批：可暂停自动推进 | 中 | 连续失败熔断；人工确认后可恢复 |

闸门误报率、伏笔归并准确率需要用标注集才能给出稳定数字。首期先记录误报/漏报样本，不把未验证的百分比写进发布门槛。

## 13. 推荐落地顺序

```text
第 1 批：验收 personality/worldview 运行态已接通；统一伏笔上下文格式
第 2 批：统一框架、卷、章三层伏笔任务，并将 CONTINUITY_BREAK/OOC_MAJOR/LOGIC_BREAK 前移为细纲驱动的轻量写前闸门
第 3 批：在 chapter_post_save 增加 narrative_state_v1 写后消化
第 4 批：增加张力趋势和文风漂移指标
第 5 批：实现带熔断和人工确认的可暂停自动推进
```

每一批都应独立测试和上线，避免同时改动 prompt、数据库、任务队列和章节保存事务，降低回归定位成本。
