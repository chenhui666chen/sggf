# 视频网关本地模拟容量测试（2026-10-14）

## 结论

本轮不调用真实供应商、不使用云资源，共发出 4372 个本地 HTTP 请求。
活动任务额度、跨 API 实例共享限流、并发幂等、模拟供应商故障恢复和
Redis 故障关闭行为均符合预期。最高档 128 个同时查询请求出现 1 次
`RemoteProtocolError`，因此最终报告 `passed=false`，不能将本轮解释为
高流量商用验收通过。原始数据见 [JSON 报告](VIDEO_GATEWAY_LOADTEST_20261014.json)。

压测发现并修复两个问题：

1. 32 个同键并发重试最初产生 1 个订单、2 个尝试、2 次模拟上游提交。
   原因是创建订单的数据库幂等约束未覆盖编排提交阶段。现增加数据库
   原子提交租约，API 重试和 worker 共用领取边界，修复后为 1 个订单、
   1 个尝试、1 次上游提交。租约到期允许中断任务继续处理；这不代表
   非幂等供应商网络结果未知时具备端到端 exactly-once 保证。
2. 本机 Redis 客户端为 6.4.0，默认连接重试使故障响应 P95 达到约 12 秒。
   生产限流客户端现显式设置零重试，保留 2 秒连接/读超时；使用同样
   构造方式重测，20 次请求全部返回 503，P95 为 2061 ms。

## 环境与测试方法

- Windows 11，Python 3.13.7，Redis 客户端 6.4.0，httpx 0.28.1，uvicorn 0.37.0。
- PostgreSQL 15 和 Redis 7 使用已有 Docker 镜像新建独立临时容器；端口只
  绑定回环地址，数据库使用 tmpfs。测试结束自动停止且移除这两个容器。
- 两个真实 HTTP API 实例运行于同一个 Python 进程的两个线程，共享真实
  PostgreSQL 仓储和 Redis Lua 令牌桶。数据库池 20、允许溢出 80。
- 使用真实 `Orchestrator`、`JobRepository` 和 `worker.run_once`，供应商
  适配器完全模拟：提交和查询调用各延迟 50 ms，生成时间设为 1 秒；
  额度验证期间人为保持排队，worker 测试时释放。
- 默认探测并发 64，活动任务上限 100；创建速率和突发设为 10000，用于
  单独验证活动任务边界，并非企业套餐默认速率或服务容量承诺。
- 限流专用阶段独立使用 1 次/秒、突发 5；查询使用应用的独立查询令牌桶。
- 客户端为固定并发的短批次闭环负载，未做长时间稳定性测试和固定到达率
  的开环测试；HTTP 延迟不计入客户端等待并发槽的时间。
- 不包含 Nginx、HTTPS、公网、OSS 下载/转存、真实风控模型、真实供应商、
  多个独立 API 进程、容器 CPU/内存限制及生产网络延迟。
- 本机依赖版本与 `router_gateway/requirements.txt` 中 Redis 5.0.1、uvicorn
  0.24.0 等固定版本存在差异，生产同版本测试仍需在 staging 完成。

## 核心结果

| 场景 | 请求/任务 | 结果 |
|---|---:|---|
| 活动额度，64 HTTP 并发 | 400 次创建 | 100 次 202，300 次活动额度 429，任务数未超 100 |
| 活动额度满时查询 | 800 次查询 | 全部 200，93.87 次/秒，P95 1710 ms |
| 两实例共享请求桶 | 100 次创建 | 5 次 202、95 次速率 429，突发额度未随实例数翻倍 |
| 同键并发重试 | 32 次创建 | 全部 202，仅 1 订单、1 尝试、1 上游提交 |
| 单 worker 收尾 | 100 个任务 | 全部成功，10.041 秒 |
| 四 worker 收尾 | 100 个任务 | 全部成功，3.436 秒，约为单 worker 的 2.92 倍速度 |
| 四 worker 与查询同时运行 | 100 任务、800 查询 | 任务全成功，收尾 4.607 秒；查询全部 200，P95 864 ms |
| 模拟供应商明确失败 | 10 个任务 | 全部成为失败终态，没有无限重建 |
| 模拟供应商断连与恢复 | 10 个任务 | 断连时保留 running，恢复后全部成功 |
| Redis 不可连接 | 20 次创建 | 全部 503，P95 2061 ms，没有绕过限流接纳任务 |

四 worker 测试调用真实 `run_once`，但批次间只等待 10 ms；生产
`run_forever` 默认忙时等待 1 秒。因此 worker 时间用于比较相同模拟
负载下的并行处理效果，不能直接推导生产任务完成时间。

worker 执行阶段还可能推进前序阶段创建的少量任务；多个 worker 对
同一未完成任务的后续轮询会增加 polls，这不等于重复提交。

## 查询并发阶梯

每档 400 次查询，在 100 个活动任务保持排队的情况下测量。

| 同时 HTTP 请求 | 成功请求/秒 | P95（ms） | P99（ms） | 结果 |
|---:|---:|---:|---:|---|
| 8 | 138.64 | 73 | 80 | 400 次 200 |
| 16 | 125.75 | 205 | 301 | 400 次 200 |
| 32 | 106.58 | 639 | 913 | 400 次 200 |
| 64 | 79.85 | 1967 | 2490 | 400 次 200 |
| 128 | 60.94 | 5130 | 5484 | 399 次 200，1 次连接中断 |

吞吐随 HTTP 并发提高反而下降，说明该本机运行方式已产生资源竞争。
未采集 CPU、连接池等待、SQL 执行计划等诊断指标，尚不能将性能下降或
连接中断归因于某一个具体组件。创建阶段总响应吞吐包含主动拒绝的
429，不能把它当作成功接单吞吐。默认活动额度测试只成功接纳 100 单，
后续请求因额度满而拒绝，也不能据此推导持续接单速率。

第三方平台可先采用 8–16 个 HTTP 并发作为本机集成测试起点，并按任务
5–10 秒间隔加随机抖动轮询。100 个活动任务每 5 秒查询一次平均约
20 次/秒，仍应分散到达，避免同时轮询形成尖峰。这是测试起点，
不构成生产 SLA 或供应商容量保证。

## 重跑方式

```powershell
python -X utf8 -m router_gateway.loadtest --output "docs/VIDEO_GATEWAY_LOADTEST_20261014.json"
```

需要本机 Docker 和已有 `postgres:15-alpine`、`redis:7-alpine` 镜像，
以及 Python 的 httpx、uvicorn、SQLAlchemy、psycopg2 和 Redis 客户端。
命令只接受负载参数和本地输出路径，不能传生产数据库地址、供应商
凭据或外部 API 地址。失败检查通过时退出码 0；出现重复提交、超额度、
意外 HTTP 错误、未完成 worker 或故障保护失败时保存结果并退出码 1。

## 后续验证边界

本轮新增回归后，网关 390 项通过、7 项云集成测试跳过，主站 36 项通过。
未执行会清空既有 PostgreSQL 测试库的两个测试文件；本轮 PostgreSQL
压测仅在自动创建的临时库内建表和写入模拟任务。

生产高流量验收应使用与部署一致的依赖、独立 API/worker 进程、Nginx
和专用测试机器，补充多客户混合流量、长时间稳定性、租约超时/进程
崩溃恢复、较长供应商响应时间等场景。真实供应商容量和成片交付仍需
另行限额验证，涉及付费调用时先获得明确预算确认。
