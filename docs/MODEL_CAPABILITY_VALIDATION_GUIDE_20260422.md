# 模型能力验证校验指南
首版日期：`2026-04-22`
适用范围：模型中心卡片维护、模型接入信息校对、后续新模型能力验证与项目内回写

## 1. 目标

这份指南用于统一后续模型能力验证的做法，避免出现以下问题：

- 只看官方文档，没有做真实调用，导致能力写得过满
- 只看一次成功返回，没有验证边界条件，导致接入后不稳定
- 供应商确实支持某能力，但项目当前链路没有透传，卡片却写成“项目可用”
- 前端模型卡、后端接入、配置文件和语义词表不同步

目标不是“证明模型很强”，而是给出一个足够保守、可复现、可回写的结论。

## 2. 核心原则

### 2.1 先区分三类结论

- `供应商文档声明支持`
- `真实接口已验证支持`
- `项目当前链路已接入可用`

这三件事不是一回事。模型卡默认应优先写第三类；如果只做到第二类，也要明确写成“已验证能力，但项目接入需继续完成”。

### 2.2 优先写“能确定的最小结论”

如果只验证到词级时间戳，就写词级已验证，不要顺手把音素级也写成支持。

如果某参数可以传，但返回里没有效果，就按“不支持”或“当前不作为能力承诺”处理，不要写成“待观察时可用”。

### 2.3 文档结论必须让位于真实调用

文档是起点，不是终点。

当官方文档、控制台、SDK 行为、项目实际调用结果不一致时，以“当前真实调用结果 + 项目当前链路行为”为模型卡口径。

## 3. 标准验证流程

建议按下面顺序执行，不要跳步。

### 第 1 步：先做文档归档

至少收集以下信息：

- 官方产品文档链接
- API 文档链接
- SDK 文档或示例链接
- 控制台模型页链接
- 项目内已有接入文件位置

对每个模型至少整理出：

- 模型 ID
- 支持的输入输出模态
- 关键参数
- 约束条件
- 响应结构
- 计费或配额说明
- 状态机或异步任务字段

### 第 2 步：列出“待验证能力矩阵”

不要直接开始试。

先把待验证项拆成矩阵，推荐最少包含：

- 基础调用是否成功
- 必填参数是什么
- 可选参数是否真的生效
- 返回结构是否符合文档
- 关键高级能力是否真实可用
- 边界条件是否报错合理
- 项目当前链路是否已经透传

### 第 3 步：做最小真实调用

第一轮只验证主链路能否跑通：

- 用最短文本、最小图片、最短视频、最少参考素材
- 只开一个目标能力参数
- 保证可以明确看出该能力是否生效

原则是“一次调用只回答一个问题”。

### 第 4 步：做结构化解析

不能只看“请求成功了”。

必须确认：

- 返回里真正出现了哪些字段
- 字段位置是否和文档一致
- 是否是增量流事件，而不是最终稳定结构
- 是否有重复数据、临时字段、仅中间态字段

例如流式接口要区分：

- `sentence-begin`
- 中间增量事件
- `sentence-end`

最终要消费哪一个，必须在验证时写清楚。

### 第 5 步：做边界验证

至少做一类失败样例：

- 超长输入
- 参数格式错误
- 不支持的模型组合
- 资源状态不合法
- 缺少前置资源

目的不是覆盖所有错误，而是确认失败方式是否可预期、是否能支撑前端提示设计。

### 第 6 步：回写项目结论

验证结束后，至少同步到下面几个位置中的相关项：

- 模型中心卡片
  - `frontend/src/pages/ModelCatalogPage.tsx`
- Asset Studio / DreamWeaver 统一模型清单
  - `backend/app/services/asset_studio_model_catalog.py`
  - `backend/app/api/v1/asset_studio_api/routes_model_catalog.py`
  - `frontend/src/hooks/useAssetStudioModelCatalog.ts`
- 模型中心实时投影层
  - `backend/app/services/model_catalog_projection.py`
  - `backend/app/api/v1/model_catalog.py`
  - `backend/app/scripts/bootstrap_model_catalog_cards.py`
- 领域/语义侧配置
  - `config/intent_domains.yaml`
  - `core/semantic_matcher.py`
- 模型画像与标签
  - `config/models.yaml`
- 项目参考文档
  - `docs/MODEL_INTEGRATION_REFERENCE.md`

如果只改了卡片，没有改统一模型清单和接入参考文档，后续继续接模型的人会重复踩坑，而且 Asset Studio / DreamWeaver 会继续显示旧选项。

如果这次变更涉及模型中心数据库快照，还应在合适时机执行：

```powershell
python -m backend.app.scripts.bootstrap_model_catalog_cards --prune-stale
```

这样可以把数据库中的模型中心条目收敛到当前集成模型集合，避免遗留测试卡片或历史废弃模型继续占库。

## 4. 状态判定标准

### 4.1 `已验证`

满足以下条件才建议标记为 `已验证`：

- 官方文档已核对
- 至少一条真实调用跑通
- 关键能力返回结构已确认
- 项目卡片中的能力描述与真实结果一致

### 4.2 `部分验证`

适用于：

- 基础链路跑通了，但高级能力未验证完
- 官方文档和真实返回仍有未解冲突
- 供应商支持，但项目链路尚未接入

### 4.3 `待手动验证`

适用于：

- 只有文档，没有做真实调用
- 或者有猜测，没有足够证据

### 4.4 `不支持`

建议在以下情况下直接标成不支持：

- 官方文档未声明，真实调用也没返回
- 参数可传但无效果
- 供应商返回明确不支持
- 项目决定不纳入能力承诺

“不支持”不等于供应商永远不支持，而是“当前项目版本下不作为可用能力”。

## 5. 按模型类型的重点检查项

### 5.1 TTS / 语音合成

至少检查：

- 是否有系统音色
- 是否必须先创建自定义音色
- `speaker` 实际传什么
- `instruction` 是否支持以及长度上限
- 是否支持音色复刻 / 设计
- `target_model` 是否必须一致
- 音色状态机字段是什么
- 是否支持词级时间戳
- 是否支持音素级时间戳
- 返回是音频 blob、URL 还是事件流

重点经验：

- 时间戳能力一定要看真实返回结构，不要只看参数名
- 事件流里经常有中间增量结果，不能直接当最终结果消费
- 如果词级有了，不要自动推断音素级也有

豆包 Seed-TTS 2.0 Expressive 额外检查：

- 模型 ID 必须记录为 `seed-tts-2.0-expressive`，默认 resource id 为 `seed-tts-2.0`。
- 非流式合成验证 `POST https://openspeech.bytedance.com/api/v3/tts/unidirectional`；双向流式能力单独验证 `wss://openspeech.bytedance.com/api/v3/tts/bidirection`。
- 鉴权检查 `X-Api-Key`、`X-Api-Resource-Id`，不要误用百炼 `DASHSCOPE_API_KEY`，也不要把火山方舟通用 `VOLCENGINE_API_KEY` / `DOUBAO_API_KEY` 当作 Seed Speech 专用 TTS Key。
- 项目只接受 `VOLCENGINE_TTS_API_KEY`、`DOUBAO_TTS_API_KEY`、`SEED_TTS_API_KEY`、`VOLCENGINE_SPEECH_API_KEY`、`DOUBAO_SPEECH_API_KEY` 作为 Seed-TTS `X-Api-Key` 来源。
- 有声小说风格控制应写入 `req_params.additions.context_texts`，不要拼入待朗读正文。
- `seed-tts-2.0-standard` 不支持 `context_texts` / `use_tag_parser`，不能用 standard 的结果证明 expressive 的高表现力能力。
- `use_tag_parser` 主要面向复刻音色和短文本精细控制，验证记录要说明是否使用复刻音色、文本长度和标签位置。
- 方括号语音标签验证要至少覆盖一个官方推荐系统音色，例如可爱女生、调皮公主、爽朗少年或天才同桌，并记录对应 `Voice_type`。
- 引用上文验证要确认上文只作为语境被理解，不被合成为音频正文。
- 当前只做本地 mock 或 payload 检查时，结论只能写“项目链路已接入”，不能写“真实接口已验证”。

### 5.2 图像生成 / 图像编辑

至少检查：

- 分辨率约束
- 批量生成上限
- 参考图数量上限
- 权重控制是否真的生效
- 编辑指令是否支持局部、重绘、扩图等
- 返回是 URL、base64 还是任务 ID

### 5.3 视频生成

至少检查：

- 时长档位
- 分辨率档位
- 首尾帧支持情况
- 图生视频 / 文生视频 / 视频续写是否分别可用
- 任务创建接口和任务查询接口是否一致
- 失败状态和轮询状态字段

### 5.4 文本 LLM

至少检查：

- 是否支持结构化输出
- 上下文长度是否真实可用
- 工具调用是否支持
- 流式输出是否稳定
- JSON 模式或 schema 模式是否真实可用

## 7. CosyVoice v3.5 Plus 的经验结论

这次验证沉淀出的经验，后续验证其他模型时可以直接复用：

- 文档里写了参数名，不代表项目链路已经透传
- 流式返回一定要分辨最终态和中间态
- 一个模型的高级能力应逐项验证，不要成组推断
- 对后续产品功能真正有价值的，不是“模型很强”，而是：
  - 前置资源是什么
  - 必填参数是什么
  - 状态机是什么
  - 最终返回长什么样
  - 哪些能力可以放心写进产品承诺

## 8. 验证结束后的最小回写清单

完成一次模型能力校验后，至少检查下面 7 项：

- 模型卡状态是否更新为正确的 `已验证 / 部分验证 / 待手动验证`
- 推荐场景是否改成真实适用场景
- 限制项是否写清楚
- API 调用页是否补了关键参数和返回结构
- AI 设计页是否只保留真正高价值的信息
- Asset Studio / DreamWeaver 统一模型清单是否同步了最新模型名称、默认值和可选项
- 参考文档是否同步到 `docs/MODEL_INTEGRATION_REFERENCE.md`

如果这 7 项没做完，就不算完成一次真正可复用的模型校验。
